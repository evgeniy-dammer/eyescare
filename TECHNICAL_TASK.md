

# EyesCare - Android-приложение для контроля дистанции до экрана

## 1. Описание проекта

**EyesCare** — это Android-приложение, разработанное для помощи пользователям в поддержании безопасного расстояния между глазами и экраном устройства. Приложение в реальном времени отслеживает расстояние с помощью фронтальной камеры и предупреждает пользователя, если он подходит слишком близко.

### Основной функционал:
- **Измерение расстояния до глаз** с использованием ML Kit Face Detection и физических характеристик камеры.
- **Коррекция на угол наклона головы** для повышения точности измерений.
- **Работа в фоновом режиме** через Foreground Service, что позволяет мониторингу работать поверх других приложений.
- **Гибкая система оповещений**: полноэкранный Overlay-баннер или, при отсутствии разрешения, уведомления высокой важности.
- **Интерактивная калибровка**: автоматическая калибровка по лицу с цветовой индикацией или ручной ввод межзрачкового расстояния (IPD).
- **Продуманный UX**: UI на Jetpack Compose в **iOS-стиле** (liquid glass, нижние табы, крупные заголовки, шрифт Inter, systemBlue), «Детский режим», кнопка аварийной остановки, экран согласия, локализация на 7 языков.
- **Eye-care**: напоминания о перерывах (правило 20-20-20) и статистика использования за неделю.
- **Экономия батареи и живучесть**: динамический FPS, пауза камеры при выключенном экране, авто-выключение при низком заряде, авто-возобновление после перезагрузки/выгрузки OEM.

### ✅ Реализовано и присутствует в коде
- **Единая `MainActivity` на Jetpack Compose** (`AppScaffold`: `Box` + Compose `NavHost` + **плавающая `NavigationBar` в стиле Telegram** — приподнята от низа, с боковыми отступами и скруглением) с **анимированными переходами** между вкладками (направленный слайд + фейд, `tween` 250 мс) и **крупными заголовками** экранов (`ScreenTitle`, iOS large title). Три вкладки:
    - **Мониторинг** (`MonitoringScreen`) — переключатель мониторинга и **живой показ дистанции**: крупное значение в см (красное при «слишком близко»), обновляется в реальном времени. Данные идут из сервиса через общий `MonitoringStateHolder` (`StateFlow`), UI подписывается через `collectAsState`.
    - **Калибровка** (`CalibrationScreen`) — превью камеры (`AndroidView(PreviewView)`), овал на Compose `Canvas`, ручной ввод IPD; камера привязана к жизненному циклу вкладки (`CalibrationController.start/stop` в `DisposableEffect`); согласие и разрешение камеры запрашиваются при входе на вкладку.
    - **Настройки** (`SettingsScreen`) — «Детский режим», выбор порога (**iOS-сегментированный контрол** `IosSegmentedControl`: серый трек + светлая нейтральная капсула у выбранного, не синяя заливка; + haptics), выбор языка и **выбор темы** (Как в системе / Светлая / Тёмная; по умолчанию — как в системе; `ThemeMode` в `MainUiState`, применяется на лету). Язык и тема открываются как **отдельные экраны в iOS-стиле** (push-детализация, `SettingsDetailScreens.kt`): список с галочкой (✓) у выбранного и кнопкой «Назад» — вместо Android-диалогов.
  Состояние — `MainUiState`; логика разрешений/сервиса/согласия/языка осталась в `MainActivity`. Тема — `EyesCareTheme`: явные контрастные **светлая и тёмная** схемы, акцент — **iOS systemBlue** (`#007AFF` / `#0A84FF`), следуют системной теме через `isSystemInDarkTheme()`. **Шрифт — Inter** (OFL, визуально близок к SF Pro; вариативный `res/font/inter_variable.ttf`) — SF Pro встраивать нельзя по лицензии Apple. **Иконки табов — контур (неактивные) / заливка (активный)**, как SF Symbols в iOS (`material-icons-extended`).
- **Стиль «liquid glass»** (`GlassSurface.kt`): цветной ambient-фон (`GlassBackground`, помечен `hazeSource`) + стеклянные карточки со светлым краем-бликом (`GlassCard`) + стеклянная нижняя панель табов. **Реальное backdrop-размытие на Android 12+** через `dev.chrisbanes.haze` (`hazeEffect`), с автоматическим откатом на полупрозрачную заливку ниже API 31. На вкладке калибровки панель — translucent-стекло поверх живого видео (камера — `SurfaceView`, backdrop-блюр к ней неприменим, `LocalHazeState` там принудительно `null`).
- **Edge-to-edge**: контент рисуется под системными барами и под панелью табов; `NavHost` помечен `hazeSource`, а панель табов (`hazeEffect`) **размывает прокручиваемый под ней контент**. Экраны получают нижний отступ на высоту бара, чтобы контент не оставался скрытым.
- Запрос runtime-разрешений: `CAMERA`, `POST_NOTIFICATIONS` (Android 13+), `FOREGROUND_SERVICE_CAMERA` (Android 14+), overlay через `ACTION_MANAGE_OVERLAY_PERMISSION` с fallback на уведомления.
- Foreground Service (`ForegroundMonitoringService`) с уведомлением, кнопкой «Остановить» и отдельным каналом предупреждений.
- Анализ кадров (`CameraAnalyzer`): CameraX + ML Kit Face Detection, выбор наибольшего лица, retry при занятой камере, реакция на смену ориентации. Чтение характеристик фронтальной камеры (`focalLength`, `sensorWidth`) вынесено в общий хелпер `CameraHardware.fetchAndSave` (используется и мониторингом, и калибровкой). Сглаживание — единственное (EMA в `DistanceCalculator`) + гистерезис; отдельный медианный фильтр убран как избыточный.
- Монокулярный расчёт дистанции (`DistanceCalculator`): формула по IPD + фокусному расстоянию в пикселях, коррекция на наклон головы (`cos` по Euler X/Y), сглаживание EMA (`ALPHA = 0.3`, сбрасывается при потере лица через `reset()`). `calibrate()` возвращает `Boolean` (успех только при наличии аппаратных параметров камеры). Класс изолирован от Android/ML Kit и покрыт unit-тестами (`DistanceCalculatorTest`).
- Оверлей-баннер (`OverlayManager`, `overlay_layout.xml`): `TYPE_APPLICATION_OVERLAY`, вибрация, кнопка экстренной остановки; fallback на heads-up уведомление при отсутствии разрешения. **Оформление в iOS-стиле**: тёмный полноэкранный фон, красный глиф-предупреждение (`ic_warning_ios`), крупный заголовок на Inter, подпись и кнопка-пилюля «Остановить» по центру. **Плавное появление/исчезновение** (fade фона + scale-«поп» контента через `ViewPropertyAnimator`, `OvershootInterpolator`).
- **Гистерезис оверлея** (`OverlayHysteresis`, ТЗ п. 6.5): включение после 3 кадров подряд ниже порога, выключение после 5 кадров подряд выше — поверх EMA-сглаживания. Логика вынесена в изолированный класс без Android-зависимостей и покрыта unit-тестами (`OverlayHysteresisTest`).
- **Ручной ввод IPD** (`CalibrationController.saveManualIpd`): кнопка сохранения подключена, значение валидируется (диапазон 40–90 мм, принимается точка и запятая), сохраняется через `setCalibratedIpd` и имеет приоритет над автокалибровкой (при сохранении анализатор отключается). Если авто-калибровка невозможна (нет аппаратных параметров камеры), показывается подсказка ввести IPD вручную (`calib_auto_unavailable`).
- Хранение настроек (`SettingsRepository`) в **`EncryptedSharedPreferences`** (Jetpack Security, AES-256): мастер-ключ в Android Keystore, автоматическое пересоздание хранилища при повреждении, исключение из бэкапа/переноса на другое устройство.
- **Экран согласия / приватности** (`MainActivity.ensureConsent`): перед первым использованием камеры (запуск мониторинга или калибровка) показывается диалог с текстом о локальной обработке и кнопкой «Я согласен»; согласие сохраняется в `SettingsRepository` и предшествует запросу разрешений (ТЗ п. 6.4).
- **Кастомная иконка приложения** (adaptive icon, `mipmap-anydpi-v26`): векторный глиф глаза на диагональном сине-голубом градиенте с глянцевым бликом в iOS-эстетике; есть monochrome-слой для тематических иконок Android 13+. Реализована как `VectorDrawable` (без растровых PNG).
- **Онбординг первого запуска** (`OnboardingScreen`): iOS-стиль (glass, systemBlue, Inter) — заголовок, подзаголовок и 5 пунктов (мониторинг / приватность-локальность / калибровка / перерывы 20-20-20 / детский режим); кнопка «Начать» прикреплена к низу экрана с пропорциональным отступом (~5% высоты), контент над ней скроллится. Показывается один раз (флаг `onboarding_done` в `SettingsRepository`); гейт в `MainActivity` перед основным UI. Проверено на устройстве.
- **Локализация на 7 языков** (английский по умолчанию, немецкий, французский, испанский, русский, итальянский, турецкий): все строки вынесены в `values*/strings.xml`. В настройках есть меню выбора языка (per-app language через `AppCompatDelegate.setApplicationLocales`) с опцией «Как в системе». По умолчанию язык берётся из системы; если системного языка нет в списке — используется английский (через дефолтные ресурсы `values/`). Для системного пикера языков (Android 13+) объявлен `locales_config.xml`.

### 🔋 Живучесть в фоне (2026-07-14)
- **Авто-возобновление**: если мониторинг был включён, но сервис убит OEM-менеджером батареи или после перезагрузки — при следующем открытии приложения сервис поднимается сам (`MainActivity.autoResumeMonitoringIfNeeded`, из foreground — легально на Android 14+). Проверено на устройстве.
- **После перезагрузки** (`BootReceiver`, `RECEIVE_BOOT_COMPLETED`): показывается уведомление «EyesCare приостановлен → нажмите, чтобы возобновить» (camera-сервис нельзя стартовать из фона на Android 14+, поэтому тап открывает приложение → срабатывает авто-возобновление). Триггерится только реальной перезагрузкой (BOOT_COMPLETED — protected broadcast, adb его не шлёт).
- **Экран «Работа в фоне»** (Настройки → Работа в фоне): запрос исключения из оптимизации батареи (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, статус «Без ограничений ✓» реактивно) + переход в автозапуск OEM (MIUI/Letv/Huawei/Coloros) с фолбэком на карточку приложения. Проверено на устройстве (диалог → whitelist → ✓; фолбэк автозапуска на кастомном ROM).
- **WorkManager-сторож** (`ResumeWatchWorker`): раз в ~15 мин проверяет «мониторинг включён, но сервис не работает» (OEM выгрузил без перезагрузки) → уведомление «возобновить»; сам отменяется при выключении мониторинга.
- **`START_NOT_STICKY`**: авто-перезапуск camera-FGS системой на Android 14+ ненадёжен (нельзя вывести while-in-use сервис в foreground из фона), поэтому восстановление только через явные пути (открытие приложения / BootReceiver / сторож).
- Примечание к релизу: `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — чувствительное для Google Play разрешение (нужно обоснование в консоли либо переход на `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`).

### 👁️ Eye-care фичи (2026-07-14)
- **Перерывы 20-20-20** (`BreakReminder` + сервис): после ~20 минут непрерывного «смотрения» (экран включён + лицо в кадре) — мягкое уведомление «Пора сделать перерыв: посмотрите вдаль ~6 м 20 секунд». Отсутствие лица ≥20 сек или выключение экрана считается перерывом и обнуляет счётчик. Переключатель в Настройках («Напоминания о перерывах (20-20-20)», по умолчанию вкл). Логика вынесена в чистый класс, покрыта unit-тестами (`BreakReminderTest`).
- **Статистика за неделю** (карточка «За неделю» на «Мониторинге»): время мониторинга, время «слишком близко», число сближений. Копится в сервисе, сбрасывается в начале новой недели (понедельник; `weekIdForEpochDay`, покрыт `UsageStatsTest`). Хранение — в зашифрованных prefs. Проверено на устройстве (время и счётчик сближений растут, карточка обновляется реактивно).

### 🔋 Оптимизация энергопотребления (2026-07-14)
- **Пауза камеры при выключенном экране** (приёмник `ACTION_SCREEN_OFF`/`ON` в сервисе): экран погас — смотреть не на что, освобождаем камеру (`CameraAnalyzer.stop()`), при включении — поднимаем (`start()`). Сам поток камеры — основной расход, так что это крупнейший выигрыш. Foreground-сервис при этом жив (иначе на Android 14+ нельзя повторно стартовать camera-сервис из фонового broadcast). Проверено на устройстве (`dumpsys media.camera`: экран off → DISCONNECT при живом сервисе, on → CONNECT).
- **Динамическое снижение FPS** (`FrameRateGovernor` + троттлинг в `CameraAnalyzer`): на безопасной дистанции анализируем ~2 кадра/с, в «зоне внимания» у порога и при потере лица — ~10 кадров/с. Логика вынесена в чистый класс и покрыта unit-тестами (`FrameRateGovernorTest`).
- **Трим ML Kit**: в детекторе монитора отключена неиспользуемая классификация (`CLASSIFICATION_MODE`), оставлены только зрачки (landmarks) и наклон головы — меньше работы на кадр.
- **Разрешение анализа ~480p** (640×480): для детекции лица на 40–60 см этого достаточно, а нагрузка на камеру/ISP/ML ниже. Полная ширина сенсора сохраняется — расчёт дистанции не меняется.
- **Ограничение частоты захвата камеры** (`Camera2Interop`, `CONTROL_AE_TARGET_FPS_RANGE` — выбирается наименьший поддерживаемый диапазон ≥15 к/с): камера снимает непрерывно и это основной расход CPU при включённом экране. На устройстве замерено: CPU в покое (экран вкл, без лица) ~54% → ~39% ядра; экран выкл — 0%; детекция не деградирует (дистанция 47,4 см).
- **Авто-выключение при низком заряде** (`ForegroundMonitoringService`): при `ACTION_BATTERY_LOW` (если не заряжается) и при попытке старта с зарядом ≤ 15% без зарядки — мониторинг не запускается/останавливается, показывается уведомление «Мониторинг выключен» и сбрасывается флаг (чтобы авто-возобновление не подняло сервис снова). Проверено на устройстве (эмуляция `dumpsys battery`).

### 🧪 Качество кода: аудиты (2026-07-15)
- **Утечки памяти:** статический аудит — настоящих утечек нет (ресурсы освобождаются симметрично, синглтоны на `applicationContext`, Compose lifecycle-scoped). Закрыты 2 огреха надёжности жизненного цикла: **L1** — гонка с асинхронным колбэком `ProcessCameraProvider.getInstance()` (флаг `@Volatile active` + ранний выход в `CameraAnalyzer`/`CalibrationController`); **L2** — неотменяемый отложенный `finishSoon` в `CalibrationController` (поле-`Handler` + `removeCallbacksAndMessages` в `stop`/`shutdown`).
- **CPU:** под контролем (динамический FPS, пауза камеры по экрану, троттлинг уведомлений, статистика по переходам) — busy-loop'ов/поллинга нет.
- **Безопасность/приватность:** уязвимостей нет. Ключевое: **нет разрешения `INTERNET`** (данные с камеры физически не покидают устройство), least-privilege, ML Kit on-device, экран согласия, `EncryptedSharedPreferences`, бэкап исключает `sharedpref`, сервис не экспортирован, `PendingIntent` — `FLAG_IMMUTABLE`, нет секретов/WebView/SQL/рефлексии, логи без PII. Отладочный `Log.d` спрятан за `BuildConfig.DEBUG`.
- Эмпирические замеры (meminfo/CPU) и проверка перезагрузкой — выполнены на устройстве (2026-07-15): утечек нет (`Activities: 1`), CPU при экране OFF — 0%, при ON — снижен ограничением FPS камеры; boot-recovery подтверждён.
- **Lint зелёный** (`./gradlew :app:lintDebug` — 0 ошибок): закрыты MissingPermission (гейт `hasPermission()`), MissingTranslation (`unit_cm` во всех локалях), UseAppTint (осознанный `android:tint`); почищены мёртвые строки, `mipmap-anydpi`, a11y-описание глифа оверлея.

### 📅 Расписание мониторинга (2026-08-31)

Постоянно включённый мониторинг мешает там, где он не нужен, — вечерний фильм, выходные, нерабочие
часы. Без расписания единственный выход был выключить приложение вручную, а выключенное вручную
приложение часто уже не включают обратно.

- **`MonitoringSchedule`** — чистый data-класс, **10 unit-тестов**. Дни недели как в
  `java.time.DayOfWeek.value` (1 — понедельник), время — минуты от полуночи.
- **Окна через полночь.** 22:00–02:00 обрабатывается корректно, и окно **принадлежит дню, в который
  началось**: ночь с понедельника на вторник попадает в расписание, если отмечен понедельник, а не
  вторник. Отдельные тесты на это и на переход через границу недели (воскресенье → понедельник).
- **Два решения, чтобы не получить бесполезное состояние:** выключенное расписание не ограничивает
  ничего (`isMonitoringAllowedAt` возвращает `true`, а не «не попадаем в окно»); совпадающие границы
  читаются как «круглые сутки в отмеченные дни», а не как пустое окно — иначе легко случайно
  выставить «расписание включено, но не работает никогда».
- **Интеграция — через уже существующий механизм пауз.** Добавлена причина `PauseReason.SCHEDULE`;
  вне окна камера отпускается, сервис остаётся foreground (иначе на Android 14+ его не поднять
  обратно). Причины складываются с остальными — есть тест на совмещение расписания со снузом.
- **Сверка по тику раз в 30 с**, а не будильником: сервис и так жив постоянно, а точность до минуты
  здесь достаточна. Плюс проверка по `ACTION_SCREEN_ON` — в глубоком сне `Handler` не тикает, ровно
  как и со снузом.
- **UI:** детальный экран в стиле остальных (переход из настроек), чипы дней и системный
  `TimePickerDialog` — он сам уважает 12/24-часовой формат и локаль. Названия дней берутся из
  `DayOfWeek.getDisplayName`, а не из ресурсов: это семь строк на семь языков, которые система уже
  знает.
- **Множественные формы.** Счётчик выбранных дней сделан через `<plurals>`, а не строку с `%d`:
  «1 days» неверно по-английски, в русском три формы. Lint при этом оказался точнее меня — указал,
  что в текущем CLDR у турецкого есть форма `one`, а у испанского, французского и итальянского
  добавилась `many` для больших чисел; все требуемые категории добавлены.

**Проверено:** сборка, **101 unit-тест** (было 90), R8-release, `lintRelease` — зелёное.
**Не проверено (телефон не подключён):** переход границы окна в обе стороны на устройстве, вид
экрана и системного выбора времени, текст постоянного уведомления вне окна.

### 🧘 Экран перерыва 20-20-20 (2026-08-31)

**Что было не так.** Напоминание о перерыве существовало как уведомление «Пора сделать перерыв /
Посмотрите вдаль около 20 секунд» — **без `setContentIntent`**. По нему было некуда нажать: текст,
который смахивают, не сделав перерыв. Самая клинически обоснованная фича приложения упиралась в
строчку в шторке.

**Что сделано.** Тап по уведомлению открывает экран перерыва с отсчётом.

- **`BreakExercise`** — чистый объект без Android и без часов, **9 unit-тестов**. Сценарий из двух
  шагов: 20 с «смотрите вдаль» (само правило 20-20-20, ради которого фича и существует) и 5 с
  «поморгайте» (против сухости — за экраном моргают реже). `progressAt(elapsedMs)` отдаёт шаг,
  остаток и долю пройденного для анимации; `displaySeconds` округляет **вверх**, чтобы ноль
  появлялся ровно в конце шага, а не за секунду до него.
- **`BreakScreen`** — намеренно почти пустой тёмный экран: на него не надо смотреть, смысл шага в
  том, чтобы смотреть ВДАЛЬ. Крупная цифра читается боковым зрением, анимация служит ориентиром:
  на первом шаге круг уменьшается, будто удаляется, на втором — сплющивается и раскрывается раз в
  секунду, задавая темп морганию.
- **Отступление от бэклога:** там значились «круговые движения глазами». Не делал — клинически
  обосновано именно правило 20-20-20, а круговые движения к нему не относятся; добавлять к
  медицинской фиче непроверенные упражнения не стал.

**Три края, закрытые сразу:**
1. **Действие интента одноразовое.** Без сброса `intent.action` система при возврате из «недавних»
   подсунула бы тот же интент, и перерыв открывался бы снова и снова.
2. **Кнопка «назад»** закрывает перерыв, а не приложение (`BackHandler`).
3. **Экран не гаснет во время перерыва** (`FLAG_KEEP_SCREEN_ON`). Перерыв длится 25 секунд, к экрану
   в это время не прикасаются, и подсветка успела бы погаснуть — а это заодно поставило бы мониторинг
   на паузу по `ACTION_SCREEN_OFF`.

`MainActivity` объявлена `singleTop` + `onNewIntent`: если приложение уже открыто, переиспользуется
существующий экземпляр, а не кладётся поверх второй.

**Проверено:** сборка, **90 unit-тестов** (было 81), R8-release, `lintRelease` — зелёное, без новых
предупреждений. Строки на все 7 языков.
**Не проверено (телефон не подключён):** внешний вид и анимация на устройстве, открытие экрана тапом
по уведомлению из шторки.

**Найден и исправлен дефект №1: перевёрнутый знак осей гравитации.** Лежащий на столе экраном вверх
телефон давал `deviceTilt = −94°` вместо +86°. Сырой замер `gravity = (0.40, 0.71, 9.77)` показал,
что датчик сообщает вектор, направленный ВВЕРХ (конвенция акселерометра), то есть «лежит» — это `+Z`,
«вертикально» — `+Y`, а у меня было `atan2(−gz, −gy)`. **Восемь юнит-тестов на эту функцию проходили,
потому что кодировали ту же неверную конвенцию во входных данных** — ровно тот класс ошибки, который
тестами не ловится в принципе и требует железа. Исправлено, тесты переписаны под замеры с устройства.

**Найден и исправлен дефект №2:** во время паузы экран показывал «Лицо не найдено. Убедитесь, что
камера вас видит» — камера выключена намеренно, и это вводило в заблуждение. Для уведомления случай
был обработан, для экрана — забыт. Теперь карточка дистанции во время паузы не показывается: карточка
паузы ниже сама объясняет, что происходит.

**Знак `headEulerAngleX` подтверждён замером.** При неподвижном вертикальном телефоне: спокойная

смотрит вверх», как и предполагалось, и порог напоминания 30° ложится ровно между нормальной посадкой
и явной сутулостью. Допущение снято → **осанка переведена в дефолт «включено»**.

**Открытый вопрос: пороги освещённости.** Замеры показали разброс, которого я не ожидал:

выдержка 60 с, но петля гистерезиса 10–30 лк лежит внутри рабочего диапазона: в записи видно, как

### ⏸️ Пауза/снуз мониторинга (2026-08-31)

Главный раздражитель мониторинга — легитимный близкий просмотр (фото, книга, показать что-то
собеседнику). Без паузы единственный выход — выключить приложение совсем, и обратно его включают
не всегда.

- **`MonitoringPause`** — чистый класс, **12 unit-тестов**. Держит *множество* причин паузы
  (`SCREEN_OFF`, `SNOOZE`), а не пару булевых флагов, потому что причины накладываются: экран может
  погаснуть посреди снуза, снуз может истечь при погашенном экране, пользователь может снять снуз,
  пока экран выключен. Камера отпускается ровно при появлении первой причины и поднимается ровно
  когда исчезла последняя — методы `pause`/`resume` возвращают именно это решение, а не состояние.
- **Сервис остаётся foreground всё время паузы**, отпускается только камера. Иначе на Android 14+
  её было бы не поднять обратно из фона — тот же приём, что уже работал для паузы по погасшему
  экрану.
- **Не конфликтует с живучестью.** `autoResumeMonitoringIfNeeded` и `ResumeWatchWorker` смотрят на
  `MonitoringStateHolder.running`, который во время снуза остаётся `true` (сервис-то жив), поэтому
  ни авто-возобновление, ни «сторож» снуз не снимают и уведомление «возобновите» не показывают.
- **Точки входа:** карточка на экране мониторинга (15/30/60 минут, показывает остаток с обратным
  отсчётом раз в секунду и кнопку «Возобновить») и **кнопка в постоянном уведомлении** — пользователь
  по определению находится в другом приложении, когда ему нужна пауза. Во время паузы уведомление
  пишет «Мониторинг на паузе», а не «лицо не найдено», и кнопка меняется на «Возобновить».
- **Две дырки в состоянии, найденные при разборе и закрытые:**
  1. `Handler.postDelayed` отсчитывает **uptime и стоит в deep sleep**, а `elapsedRealtime` — идёт.
     Снуз, истёкший во время сна устройства, держал бы камеру до срабатывания таймера уже после
     пробуждения. Поэтому по `ACTION_SCREEN_ON` сначала проверяется просрочка снуза, потом снимается
     причина «экран».
  2. Смена состояния снуза шла через тот же троттлинг уведомления (1/сек), что и обновления
     дистанции, и могла быть проглочена. Добавлен `force` для смены состояния.

### 🧍 Напоминание об осанке (2026-08-31)

- **Почему одного угла ML Kit мало.** В бэклоге значилось «углы наклона головы уже считаются — данные
  есть». Данные есть, но `headEulerAngleX` описывает поворот лица **относительно камеры**. Телефон
  лежит на столе экраном вверх, человек смотрит на него сверху — камера видит лицо фронтально
  (`headEulerAngleX ≈ 0`) при согнутой почти на 90° шее. Один этот угол пропустил бы ровно самый
  частый случай «text neck».
- **Решение:** к углу лица добавляется наклон самого устройства, взятый из вектора гравитации.
  `PostureMath` (**8 unit-тестов**) — две чистые функции: наклон устройства от вертикали через
  `atan2` по осям Y/Z и `neckFlexionDeg = deviceTilt − headEulerX`. Формула выведена и проверена на
  крайних случаях: телефон вертикально + лицо фронтально → 0°; телефон лежит + лицо фронтально → 90°;
  телефон вертикально + лицо опущено на 20° → 20°.
- **`PostureMonitor`** — пороги предметной области: напоминаем выше 30° (общепринятая граница
  заметного роста нагрузки на шейный отдел), отпускаем ниже 20°, выдержка 60 с, пауза 30 мин.
- **По умолчанию ВЫКЛЮЧЕНО**, в отличие от остальных напоминаний. Расчёт опирается на знак
  `headEulerAngleX` у ML Kit («плюс — лицо смотрит вверх»), а это внешнее допущение, не проверенное
  на устройстве. Если знак окажется обратным, включённая по умолчанию фича слала бы напоминания
  людям с правильной посадкой. **Включить по умолчанию после проверки на реальном телефоне** —
  правка в одну строку в `SettingsRepository.isPostureWarningEnabled`.

### ♻️ Рефакторинг: `SustainedThreshold` (2026-08-31)

Гистерезис + выдержка + пауза между напоминаниями понадобились второй раз (тёмная комната и осанка),
поэтому логика вынесена в общий чистый класс `SustainedThreshold` (**9 unit-тестов**, проверяется в
обе стороны сравнения). `AmbientLightMonitor` и `PostureMonitor` стали тонкими обёртками, хранящими
только пороги своей предметной области. Рефакторинг проверен тем, что **все 10 ранее написанных
тестов `AmbientLightMonitorTest` прошли без единой правки**.

Направление сравнения выводится из порядка порогов и читается прямо в месте создания:
`SustainedThreshold(enterAt = 10f, exitAt = 30f, …)` — «включиться, когда упало ниже 10»;
`SustainedThreshold(enterAt = 30f, exitAt = 20f, …)` — «включиться, когда поднялось выше 30».

**Итого по обеим фичам:** сборка, **80 unit-тестов** (было 51), R8-release, `lintRelease` — зелёное,
без новых предупреждений. **Не проверено (нет устройства):** знак `headEulerAngleX`, пороги наклона
в реальной посадке, поведение снуза на настоящем цикле сна устройства, кнопки в уведомлении.

### 💡 Предупреждение о тёмной комнате (2026-08-31)

Первая фича из бэклога. Яркий экран в тёмной комнате — самостоятельный фактор зрительного утомления
(контраст между экраном и окружением), не связанный с дистанцией.

- **`AmbientLightMonitor`** — чистый класс без Android и без часов (время подаёт вызывающий),
  10 unit-тестов. Три механизма против назойливости:
  1. **гистерезис** — «темно» ниже 10 лк, «светло» выше 30 лк; между порогами состояние держится
     прежним, поэтому колебания на границе не дёргают предупреждение;
  2. **выдержка 60 с** непрерывной темноты — случайная тень, ладонь над датчиком или проход мимо
     лампы ничего не запускают;
  3. **пауза 30 мин** между предупреждениями — если человек решил не включать свет, мы не повторяем
     напоминание. Пауза переживает и включение-выключение света, и паузу мониторинга по погасшему
     экрану: иначе в тёмной комнате каждое включение экрана приносило бы новое напоминание.
- **Проводка:** `SensorEventListener` на `Sensor.TYPE_LIGHT` в `ForegroundMonitoringService` рядом с
  `batteryLowReceiver`/`screenReceiver`; подписка живёт по циклу камеры (старт / экран погас /
  экран зажёгся / `onDestroy`), `SENSOR_DELAY_NORMAL`. Уведомление — `showDarkRoom()` в
  `MonitoringNotifications`, **в собственном канале**, чтобы его можно было приглушить в системных
  настройках отдельно от остальных. Тумблер в настройках (по умолчанию включён), строки на все
  7 языков.
- **Почему это ничего не ломает:** датчик света не требует разрешений, не трогает камерный пайплайн
  и не участвует в `FrameRateGovernor`. Настройка проверяется в слушателе, а не при подписке —
  тумблер можно переключить на работающем сервисе без переподписки. На устройствах без датчика
  `getDefaultSensor` вернёт `null` и фича молча выключается; в манифесте объявлено
  `uses-feature android:required="false"`, чтобы Play не фильтровал такие устройства.
- **Проверено:** сборка, 51 unit-тест (было 41), R8-release, `lintRelease` — зелёное, без новых
  предупреждений.
- **Не проверено (нет устройства):** реальные значения люксов. Пороги 10/30 лк — расчётные ориентиры
  (лунный свет ~1 лк, тёмная комната ~1–10 лк, настольная лампа ~50 лк, офис ~300–500 лк); датчик
  стоит рядом с экраном и частично ловит его собственную подсветку, поэтому пороги стоит уточнить
  замером на телефоне.

### 🔒 Не реализовано: родительский PIN-замок (спроектировано 2026-07-15, решено пока не делать)

**Цель.** Родитель включает мониторинг на устройстве ребёнка; ребёнок не может выключить его или
ослабить настройки без 4-значного PIN. Опциональная фича (по умолчанию выключена — для взрослого,
который ставит приложение себе, PIN не нужен).

**⚠️ Ограничение платформы (принять до реализации, не переобещать в описании/сторе).**
App-level PIN защищает только от «тапнул тумблер». Он **не** мешает обходу через ОС: Настройки →
«Остановить принудительно» / очистить данные / удалить приложение / отозвать разрешение камеры.
Настоящая защита от этого — только Device Admin / Device Owner (managed device) или kiosk-режим:
тяжело, чувствительно для Google Play, другой класс приложения — **вне объёма**. Частичная компенсация
уже есть: авто-возобновление сервиса + `BootReceiver` + `ResumeWatchWorker` (если ребёнок убил сервис —
поднимется). Формулировка ценности: «нельзя выключить в один тап», а не «нельзя обойти».

**Точки запроса PIN** (только когда PIN включён):
- выключить мониторинг (тумблер на «Мониторинге» + кнопки «Остановить» в уведомлении и на оверлее — их
  тоже гейтить, иначе дыра);
- отключить «Детский режим»;
- изменить порог дистанции;
- экран «Работа в фоне» (там можно ослабить живучесть);
- сам экран «Родительский контроль» (смена/снятие PIN).
- Включение мониторинга и ужесточение настроек PIN **не** требуют — это «безопасное» направление.

**Хранение и безопасность** (secure-by-default, поверх текущего `EncryptedSharedPreferences`):
- Хранить **солёный хэш** PIN (не плейнтекст): случайная соль + SHA-256/PBKDF2, в `SettingsRepository`
  (уже AES-256, KeyStore-bound). Хэш — defense-in-depth, чтобы PIN не был восстановим даже при
  компрометации хранилища.
- **Анти-брутфорс**: 4 цифры = 10 000 комбинаций; ввести лок/растущую задержку после N неверных попыток
  (напр. 5 попыток → таймаут; счётчик и время последней попытки — в зашифрованных prefs).
- **Сброс/забыли PIN**: без сервера восстановление = очистка данных приложения (сбрасывает всё,
  включая PIN). Явно написать это на экране PIN. Опционально — контрольный вопрос (менее безопасно,
  скорее не надо).

**UI (в стиле iOS, как остальное приложение):**
- Экран «Родительский контроль» в Настройках: переключатель «Защита PIN-кодом», кнопки «Задать PIN» /
  «Сменить PIN» / «Снять PIN» (снятие — под текущим PIN).
- Экран ввода PIN: 4 точки-индикатора + цифровая клавиатура на Compose (iOS-стиль), haptics, тряска при
  ошибке, отсчёт при локе. Показывается модально в точках запроса.
- Локализация всех строк на 7 языков.

**Изоляция логики / тестируемость:** проверку/хэш/лимит попыток вынести в чистый класс (напр. `PinLock`:
`verify(input): Result`, `isLockedOut(now)`, `setPin`) без Android-зависимостей — покрыть unit-тестами,
как `DistanceCalculator`/`OverlayHysteresis`.

**Файлы (ориентировочно):** `PinLock.kt` (чистая логика + тесты), экран(ы) в `SettingsDetailScreens.kt`
или новый `PinScreens.kt`, ключи/методы в `SettingsRepository`, гейты в `MainActivity`
(тумблер/настройки) и в `MonitoringNotifications`/`OverlayManager` (кнопки «Остановить»).

## 2. Ключевые реализованные функции

В ходе разработки MVP был реализован следующий функционал:

- **Современный и адаптивный UI**:
    - Единая `MainActivity` на **Jetpack Compose** с нижними табами (Compose Navigation): Мониторинг / Калибровка / Настройки. Тема `EyesCareTheme` (Material 3 + dynamic color).
    - На XML Views остаётся только оверлей-баннер (показывается через `WindowManager`).
    - Макеты адаптированы для корректного отображения на устройствах с разным размером экрана (включая планшеты).

- **Продвинутая система калибровки**:
    - Реализована **автоматическая калибровка**, где пользователю достаточно поместить лицо в интерактивный овальный контур.
    - Добавлена **визуальная обратная связь** (смена состояния овала через `isSelected`/`isActivated`) для интуитивного процесса.
    - Реализована возможность **ручного ввода IPD** для продвинутых пользователей: значение валидируется (40–90 мм), сохраняется и имеет приоритет над автоматической калибровкой (`SettingsRepository.getIpdMm()` отдаёт приоритет откалиброванному значению).

- **Точный алгоритм расчета дистанции**:
    - Приложение считывает физические характеристики камеры (`focalLength`, `sensorWidth`) для использования в формуле.
    - Реализована **коррекция на углы наклона головы** (Euler Angles), что значительно повышает стабильность и точность измерений.

- **Надежность и обработка ошибок**:
    - Реализован механизм **повторных попыток (`retry`)**, если камера временно занята другим приложением.
    - Реализован **fallback-механизм**: при отсутствии у приложения разрешения на оверлей, оно переключается в режим оповещений через Heads-up Notifications.

- **Качество кода и архитектура**:
    - Проведен **рефакторинг `DistanceCalculator`** для полного отделения логики от зависимостей Android/ML Kit.
    - Написаны **Unit-тесты** с использованием Mockito, покрывающие основную логику расчетов и калибровки.

- **Продуманный UX**:
    - Реализован гибкий **"Детский режим"**, который предлагает более безопасный порог по умолчанию, но оставляет родителям контроль над настройками.
    - Добавлены **кнопки аварийной остановки** сервиса в уведомление и на оверлей.

## 3. Инструкция по запуску и использованию

### Требования
- Android Studio (актуальная версия с поддержкой AGP 9.x)
- JDK 11+
- Gradle 9.4.1 (используется wrapper), Kotlin 2.2.10
- Устройство или эмулятор с Android 8.0 (API 26, `minSdk`) или выше и рабочей фронтальной камерой.
- `compileSdk`/`targetSdk` = 36 (Android 16). Приложение работает на Android 8+ (`minSdk` = 26).
- В `local.properties` должен быть указан путь к Android SDK (`sdk.dir`).

### Первый запуск

1.  **Установите и откройте приложение**.
2.  **Активируйте переключатель «Мониторинг расстояния»**. При первом использовании камеры появится **экран согласия** с информацией о том, что обработка ведётся локально; нажмите «Я согласен». После этого приложение последовательно запросит необходимые разрешения:
    - **Доступ к камере**.
    - **Отправка уведомлений** (на Android 13+).
    - **Отображение поверх других приложений**. Вы будете перенаправлены на системный экран, где нужно активировать переключатель для EyesCare.

### Калибровка (Важный шаг!)

Для максимальной точности рекомендуется пройти калибровку. Перейдите на экран **«Пройти калибровку»**.

- **Автоматический способ (рекомендуется)**:
    1.  Расположите устройство на расстоянии примерно 30 см от лица.
    2.  Поместите ваше лицо в овальный контур на экране.
    3.  Когда лицо будет распознано, овал станет желтым. Держите телефон неподвижно.
    4.  Как только вы займете правильное положение, овал станет зеленым, и начнется автоматическая калибровка. 
    5.  После успешной калибровки вы увидите `Toast`-сообщение, и экран закроется.
- **Ручной способ**:
    - Если вы знаете своё межзрачковое расстояние (IPD), введите его в миллиметрах (40–90 мм) в поле внизу экрана и нажмите кнопку сохранения. Этот метод имеет приоритет над автоматическим.

### 5.2. Требования к UI/UX
- **Целевой стиль — iOS (принятое направление).** Интерфейс переводится на iOS-эстетику:
    - **liquid glass** — полупрозрачные размытые поверхности;
    - **нижняя панель табов** для основной навигации;

- **Текущее состояние**: **iOS-редизайн по плану завершён.** Single-Activity на Compose с нижними табами (`AppScaffold` + Compose Navigation: Мониторинг / Калибровка / Настройки), живой показ дистанции (`MonitoringStateHolder`/`StateFlow`), стиль liquid glass (`GlassSurface.kt`), кастомная иконка. ViewBinding удалён. На XML Views остаётся только оверлей-баннер (`overlay_layout.xml`, показывается через `WindowManager`).
- **Про glass**: на Android 12+ (API 31) — истинное backdrop-размытие Compose-контента (haze/`RenderEffect`); ниже — полупрозрачная заливка. Живое видео камеры (`SurfaceView`) размыть нельзя — там всегда translucent-стекло.

## 6. Изначальный промпт (Архив)

*Этот раздел содержит оригинальную версию технического задания, на основе которого стартовала разработка.*

Ты — мой инженерный ассистент по Android-разработке (Kotlin).
Помоги спроектировать и реализовать MVP Android-приложения, которое в реальном времени отслеживает расстояние от экрана устройства до глаз пользователя с помощью фронтальной камеры, предупреждает при слишком близком расстоянии с помощью полноэкранного неубираемого overlay-баннера, и работает поверх других приложений в фоновом режиме через Foreground Service.

Приложение разрабатывается только под Android, без iOS.
Все вычисления выполняются строго локально на устройстве, кадры камеры не сохраняются и не отправляются.

### 6.1. Описание проекта (суть)

- Android-приложение на Kotlin (Android Studio).
- Проект создан как Empty Project (No Activity).
- Цель: помочь пользователю (взрослый или ребёнок) соблюдать безопасное расстояние между глазами и экраном смартфона/планшета.
- Основной функционал:
  - измерение расстояния «глаза ↔ экран» в реальном времени;
  - предупреждение при превышении порога (слишком близко);
  - показ полноэкранного overlay-баннера поверх любых приложений (YouTube и т.д.);
  - работа в фоне через Foreground Service;
  - калибровка расстояния и IPD;
  - управление настройками (порог в см, вкл/выкл мониторинга).

### 6.2. Стек и технологии

Использовать нативный Android (Kotlin).

Основные технологии:
- CameraX (camera-core, camera-lifecycle, camera-view).
- ML Kit Face Detection — базовая реализация (landmarks, bounding box, Euler angles).
- MediaPipe Face Mesh (опционально) — более плотные landmarks для повышения точности.
- ARCore Depth API — использовать при доступности для прямого измерения глубины (fallback на монокулярный алгоритм).
- Kotlin Coroutines.
- Android Lifecycle.
- Material UI.
- Vibrator API (вибрация при показе баннера).

### 6.5. Поведение overlay-баннера (UX)

- При появлении:

- Emergency area:
  - кнопка «Домой» / «Экстренный вызов»; 
  - нельзя блокировать системные критические функции.

Debounce (обязательно):
- Включение баннера: 3 кадра подряд ниже порога.
- Выключение баннера: 5 кадров подряд выше порога.

### 6.7. Алгоритм оценки расстояния
   
Приоритет источников:
- ARCore Depth API — если доступно.
- Монокулярный алгоритм по IPD + параметрам камеры.

Монокулярная формула:
- Получить:
  - f_mm — focal length из CameraCharacteristics;
  - sensor_width_mm;
  - image_width_px.
- Рассчитать:
  - f_pixels = (f_mm / sensor_width_mm) * image_width_px;
  - distance_mm = (f_pixels * real_ipd_mm) / pixel_ipd.
- pixel_ipd — расстояние между глазами (landmarks).

IPD:
- Default:
  - взрослый: 63 мм;
  - ребёнок: 54 мм.
- Поддержать калибровку IPD.
- Детский режим:
  - более консервативный порог;
  - больше сглаживание.

Коррекции и устойчивость:
- Наклон головы:
  - использовать Euler angles;
  - корректировать pixel_ipd по cos(pitch).
- Частичная видимость:
  - fallback: nose-to-eye / bounding box width.
- Несколько лиц:
  - выбирать лицо с наибольшей площадью bounding box.
- Фильтрация:
  - медиана последних K значений;
  - EMA;
  - отсев выбросов.
